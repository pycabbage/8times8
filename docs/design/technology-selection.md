# 8 times 8 — Rust リライトの技術選定

## 結論

**ゲームの状態とルールは純 Rust に集約する。盤面は固定幅整数と疎な 8×8 階層、経済値はレベルごとの厳密な非負整数とする。** 経済値の初期候補は `u128` から `num-bigint::BigUint` への昇格方式。Linux x86-64 GNU でまず描画・保存なしのコアを検証し、その後 `winit` + `wgpu` でネイティブデスクトップ版を新規実装し、Vulkan を実機で測る。Windows は後続の配布候補、Web 版は初期開発・配布の対象外とする。

性能上の優先順位は、**全体走査・境界の反復を減らす → 描画・保存・UI への転送量を抑える → プロファイルに基づき多倍長バックエンドを詰める**。原版（`vendor/`、`cfec14a`）の観察と候補の一次資料に基づく方針であり、候補の性能順位ではない。原版の限定的な実測、静的な見積もり、採否の数値目標は区別する。

## 原版と配布対象

- 『8 times 8』は白タイルを裏返し、完成した区画を起点に盤面を広げるゲーム。1A は 64 枚、1B 以降は直下レベルの 64 区画で、最高レベルは 1H。1D・1F・1H 到達で、新規開放時の大タイル候補の上限がそれぞれ 1B・1D・1F に上がる。既に開放・完成した領域がある場合は、未使用の小さい候補か通常の 1A に戻る。完成報酬・残高・支出はレベルごとに独立し、レベル間では換算しない。手動強化と、A〜E の自動機械（通常は各 4 台まで）がある。根拠：[盤面・状態](../../vendor/main.js#L41-L68)、[大タイル候補](../../vendor/main.js#L186-L225)、[報酬](../../vendor/main.js#L339-L384)、[ポイント計算](../../vendor/main.js#L99-L103)、[機械の購入](../../vendor/main.js#L1677-L1698)。
- `vendor/` はルール・動作の参照、差分試験、ベースライン計測にだけ使う。ソース（HTML/CSS/JS、Canvas 2D、Electron ラッパーを含む）、画像・アイコン・音などの資産は再利用も同梱もしない。UI・描画・素材・音は新規に作り、原版の見た目・演出やファイル構成は製品要件にしない。旧セーブの移行も初期要件ではない。
- 初期のビルド・計測対象は Linux x86-64 GNU（`x86_64-unknown-linux-gnu`）、正式 CI は GitHub Actions の Linux runner とする。Linux の対応環境、Windows 配布の可否、必要になった場合の Web の条件は後述する。

## 数値の分離と互換性

| 領域 | 原版の実態 | 選定 |
| --- | --- | --- |
| タイル・区画内の進捗 | 1A は `lo`/`hi` 各 32 ビット、反転済み枚数は 0〜64。1H 内の総枚数は `64^8 = 2^48`、各レベルの子孫数もその範囲内。ここでは `Number` の整数精度で足りる（[定数・状態](../../vendor/main.js#L41-L97)、[進捗伝播](../../vendor/main.js#L246-L253)、[完成処理](../../vendor/main.js#L344-L417)）。 | 1A は `u64` のマスクにまとめ、枚数は `count_ones`（必要なら `u8` でキャッシュ）、子の完了数は `u8`、区画内の枚数・子孫数は `u64`。完了区画を個々のタイルに展開しない。 |
| 座標・描画 | 文字列キー `x,y`。親座標は `floor((u+4)/8)`。ヒット判定、カメラ、ズーム、表示用進捗率は `Number`（[親座標](../../vendor/main.js#L34-L53)、[カメラ](../../vendor/main.js#L786-L810)、[描画比率](../../vendor/main.js#L1403-L1417)、[ヒット判定](../../vendor/main.js#L1468-L1491)）。 | 型付き整数キー `(level, x: i64, y: i64)`。親座標は `(u+4).div_euclid(8)` とし、加算・逆変換・範囲計算は検査付きの広い中間型を使う。`i64` 全域では距離の二乗和が `i128` に収まるとは限らない。座標域は隣接・端点、機械位置の小数刻み、中心・相対位置、ワールド座標と描画原点の投影まで含め、各単位と中間型を組で定めて演算前に検査する。描画は整数原点に対する相対値で補間を `f64`、GPU 入力を `f32` とする。 |
| 作業量と機械段階 | 手動は 16 段まで（最大 `2^24` 枚）。機械の指数は `e = 6*(tier-1)+stage`、実効作業量は `2^min(e,52)`。一手は対象からその祖先へ進み 1H で止まる（[容量・強化](../../vendor/main.js#L121-L150)、[作業の範囲](../../vendor/main.js#L613-L634)）。 | 段階は検査付き `u32`、指数計算は `u64`、作業量も `u64`。**シフト前に `e` を 52 に制限**する。意味のない `2^e` の多倍長展開はせず、区画の総枚数 `2^48` とは別に、実効上限 `2^52` をルール値として保つ。 |
| ポイント・価格 | レベル `L` ごとに `avail(L) = max(0, BigInt(cleared[L]) + debugBonus[L] - spent[L])`。`spent[L]` と `debugBonus[L]` は `BigInt`、累計完成数 `cleared[L]` は `Number` なので `2^53-1` 超の整数更新を保証できない。固定の本体・手動価格と、機械の `20 * 3^stage` がある（[ポイント](../../vendor/main.js#L65-L66)、[残高・支払い](../../vendor/main.js#L99-L103)、[価格](../../vendor/main.js#L129-L150)、[報酬の更新](../../vendor/main.js#L359-L374)）。 | `cleared[L]`・`bonus[L]`・`spent[L]` を各レベル別の厳密な `Amount` で保持し、他レベルからは充当しない。主な演算は加算、比較、非負差、×3、取込時の有界累乗、表示の定数除算・十進変換。支払いと段階更新はともに確定し、残高不足や上限超過ならどちらも変えない。差が負ならそのレベルの利用可能額を 0 とする。 |

桁の省略表示・機械の表示寸法は新規 UI で決め、支払いや保存には使わない。1A〜1H を超える作業量は巨大な整数を展開せず `2^e` と実効上限で示す。価格・加算・支出は浮動小数点や仮数・指数の近似型に置き換えない。

### 多倍長バックエンド

| 候補 | 採否と理由 |
| --- | --- |
| Rust 標準の `u64` / `u128`、固定幅の [`bnum`][bnum] | 盤面は標準型を採用し、経済の小さい値には `checked_*` 付き `u128` を使う。単独の `u128` は価格だけでも `stage=79` で不足し、`U256` でも `stage=159` で不足する。`bnum` の `U4096` なら下記の格納上限に対応するが、各値が桁数にかかわらず 512 バイトで、上限変更に型幅の変更が要る。固定幅で足りると合意できた場合、または桁がほぼ一定の負荷向けの対照候補。`bnum` は MIT OR Apache-2.0。 |
| 純 Rust の [`num-bigint::BigUint`][num-bigint] / [`dashu_int::UBig`][dashu] | **暫定採用は `Amount::Small(u128)` / `Amount::Large(BigUint)`**。必要な値だけ動的に昇格し、大きい値では参照や代入演算で不要な clone・型変換を避ける。`BigUint` 単体と `UBig` 単体も必ず対照にする。どちらも MIT OR Apache-2.0 で C のビルドを追加しない。 |
| [`rug::Integer`][rug] + [GNU GMP][gmp] | Linux 上で整数演算を比較計測するためだけの対照。純 Rust の対照も同じ GNU ターゲット・ツールチェーンでビルドする。製品・正式 CI の依存にも、バックエンドの切替候補にも入れない。 |

[`num-bigint` 0.5.1 の `BigUint`][num-bigint-inline] は 1 limb をインラインに保持できる（0.4.7 から）。[`dashu-int` 0.6.2 の `UBig`][dashu-inline] は 2 limb。インライン格納の上限はそれぞれ x86-64 で 64／128 ビット、`wasm32` で 32／64 ビットになるため、小額なら自前の昇格方式が速いとは限らない。これらは参照した版の内部表現であり、演算中の確保件数・速度は測って判断する。

`Amount` はコア内部の型とし、保存や UI にライブラリー固有の limb 配列・型名を出さない。購入後は次回価格を `価格 × 3` で更新し、同じ段階の価格と表示文字列を再利用する。ロードで段階へ飛ぶときだけ有界の整数累乗を使う。`avail` と表記は通貨残高・段階が変わった箇所だけ再計算し、ショップが閉じている間は価格の表示変換をしない。

**有限資源と厳密性の境界。** 初期検証では、格納する各経済値の上限を 4,096 ビット（`MAX = 2^4096 - 1`、十進で最大 1,234 桁）とする案を試す。盤面の展開件数・レコード長・保存容量の上限も代表データと実機性能から決める。桁数・符号・レコード数・座標と単位の範囲は大きな確保の前に検査し、桁数が同じでも上限値そのものと比較する。`cleared[L] + bonus[L]` の中間値と利用可能額 `avail(L)` は格納幅より最大 1 ビット広くても切り詰めず厳密に扱う。支払いは `avail(L)` と `MAX - spent[L]` の両方に収まる場合のみ成功させる。上限・容量超過で拒否する場合は確定済み世代を変えない。

この上限なら `20 * 3^stage` が格納できる最後の段階は 2,581（式から求めた値）。段階 2,581 で支払えた場合は購入を確定し、段階 2,582 の次回価格を上限超過マーカーにする。ロードでも段階を先に比較し、2,582 以上では累乗を起動せず購入不可とする。価格と実効作業量は別なので、許容範囲の段階の機械は動かせる。許容外のセーブは原本を保持したまま拒否し、桁の切り詰めや無制限のメモリー確保はしない。

## 負荷の仮説と盤面構造

| 優先して測る箇所 | ソースから分かる増え方 | リライト方針 |
| --- | --- | --- |
| 区画完成・境界開放・ロード | [`cleanupInside`](../../vendor/main.js#L322-L337) は高レベル完成時に盤面の `Map` などを全走査し、下位集合のキーを複製・再解釈する。[`openAround`](../../vendor/main.js#L421-L439) は辺の 1A ごとに `touch` を呼ぶ。1H 一つなら静的に `4 * 8^7 = 8,388,608` 回で、開放物の実数とは異なる。[ロード](../../vendor/main.js#L686-L744)でも完成区画の周囲を開き直す。 | 下位報酬は集計差分で確定し、対象部分木だけを完了ノードへ畳む。境界は完成時に開放結果を順序付き範囲で確定し、必要な箇所の物理レコードだけを具体化する。新形式のロードでは、確定済みの論理境界を復元する。 |
| 反転・再探索 | [`fillUnit`](../../vendor/main.js#L509-L551) は予算が足りれば一区画を一括完了する一方、部分処理では最大 64 子を最大 64 回探す経路がある。[`flipSome`](../../vendor/main.js#L563-L582) は反転ごとに祖先を更新する。 | ビットマスクで有効な候補だけを絞り、部分反転の祖先更新を同じブロック内でまとめる。完了が起きたら、次の選択前に候補を即時更新する。走査の削減で作業順・報酬・開放を変えない。 |
| 機械のターゲット探索 | [`botTarget`](../../vendor/main.js#L1917-L1950) は現在地で仕事ができないと、大タイルと通常ブロックをそれぞれ走査する。他機が使っていない 1A があればそちらを優先し、その結果と大タイルを距離比較する。 | 同じ空間階層に対象の有無を集計し、最近傍探索で距離下限による枝刈りを行う。現在の対象を優先する規則、他機の予約とフォールバック、走査順の同距離 tie-break を保持する。走査順をハッシュ反復順に委ねない。小盤面の直接走査と比較し、索引維持の費用も測る。 |
| 描画・アニメーション | 視野と LOD は既にあるが、ブロックは視野の面積と総件数の小さい方を走査し、[複数の描画パスやアニメの後始末](../../vendor/main.js#L857-L982)・[大タイルと完成区画](../../vendor/main.js#L1403-L1465)は視野外の集合も調べる。縮小中も部分反転 1A は[セル単位](../../vendor/main.js#L1341-L1366)でパスを作る。 | 視野に交差するノードだけを列挙し、新規レンダラーで画面上の寸法に応じて集約する。表示専用の集約は 1H より上にも置けるが、ゲームルールのレベルや論理ヒット判定を変えない。演出向けの差分・寿命は盤面とは別に管理する。 |
| セーブ・ショップ | [`saveNow`](../../vendor/main.js#L650-L674) が盤面列挙、JSON 化、同期 `localStorage` 書き込みを行う。通常は初回要求から 400 ms 後、[購入](../../vendor/main.js#L1664-L1674)などはその場で保存。[ショップ](../../vendor/main.js#L1604-L1655)は開いていると行ごとに価格のべき乗と整形を行う。 | 保存は UI スレッドから分離し、変更チャンクと世代でまとめる。UI は残高・価格・ボタン状態の差分だけを受け取る。進行中の操作は保存せず、確定済みの同一世代を使う。 |

最上位ノードは疎な整数キーの索引、各子集合は占有マスクと連続領域（少数なら疎な格納、密なら配列）を基本とする。盤面全域を確保せず、占有・進捗・子孫報酬は変更ノードと祖先だけで再集計する。祖先の進入可否は初期案ではキャッシュせず、[固定深さの祖先・隣接判定](../../vendor/main.js#L193-L213)で再判定する。キャッシュが実測で必要になった場合だけ、完成による影響を下位まで含む隣接帯に限定して無効化する。

**論理境界は完成時に確定する。** 開放順は [1A では東西南北、上位では辺のオフセットごとに西東北南](../../vendor/main.js#L421-L439)。その順に祖先の進入可否・占有・候補レベルを判断し、論理開放と登録順位を確定する。[群の最初の有効接触](../../vendor/main.js#L279-L303)では未使用の子を行優先で開放し、子ごとの進入再判定は行わない。遅延するのは物理レコードの展開だけであり、後の照会・カメラ移動・範囲分割・保存／ロード順で過去の接触を再判定したり順位を振り直したりしない。

**作業経路は分ける。** [作業処理](../../vendor/main.js#L501-L582)の対象は、通常 1A なら開放済み・未完・進入可能、上位なら盤面に存在し未完の区画。群として開く大タイルに子自身の隣接条件は課さない。予算による一括完了を先に判定する。不足なら 1A は起点から行優先で一周して白ビットだけを処理し、大タイル群は起点の子から行優先で一周する（起点が群の外なら最近傍の有効な子から）。普通の上位区画では操作の起点に最も近い有効な子を毎回選び直す。子の同距離判定は行優先。大タイル単体の部分作業は進捗だけを増やす。レベル `L` の完成は `j = L` に 1、`j < L` に `64^(L-j) − 既報酬数` を加え、64 子目の親連鎖でも二重計上しない。[報酬 → 境界開放 → アイテム → 親の連鎖完成](../../vendor/main.js#L339-L418)の順を保ち、普通の区画・作業群の完成は辺を開くが大タイル単体の完成では開かない。

**機械は優先度と登録順も比較する。** [探索](../../vendor/main.js#L1917-L1950)は現在の有効な大タイル、現在の 1A 内の白ビット巡回を先に試す。広域では未予約の通常 1A の最近傍を選び、なければ予約済みの最近傍を採る。その結果と大タイルの最近傍を比較し、同距離なら通常 1A を優先する。同種の同点は通常 1A が登録順、大タイルがレベル昇順・登録順。広域で新たに選んだ 1A には最近傍の白タイルから入る（同点は行優先）。有効な旧 1A の予約は大タイルへ移動中も残り得る。同距離でより早い順位が残る枝は刈らない。[移動開始・到着](../../vendor/main.js#L1953-L1984)で対象を再検証し、作業量は到着時点の段階で決め、同時刻の処理順は安定した受付連番で決める。通常 1A 到着時は予約ビットの白黒を再検査せず、区画が有効なら予約時のビットを作業の起点とし、部分反転ではそこから巡回する。

照合対象は論理状態と操作順。原版の[約 1,200 ms の演出用削除待ち](../../vendor/main.js#L305-L337)が入力ヒットや機械選択・予約に漏れる挙動、および[アイテム取得途中の同期保存](../../vendor/main.js#L481-L492)は再現しない。完了部分木を論理上すぐに畳み込み、保存は確定世代だけを対象とする。旧アニメーションや効果音も照合しない。

## 実行・描画・保存の構成

| 層 | 選定 |
| --- | --- |
| `core` | Rust stable。盤面・経済・購入・アイテム・期限順の機械スケジュールを保持する。headless 入力は操作列、論理位置、時計、乱数などに限る。カメラに由来する機械の初期位置も論理座標の引数で渡し、コアからカメラを参照しない。UI・OS・GPU・音声・保存には依存しない。 |
| ネイティブ | [`winit`][winit] のイベントループと [`wgpu`][wgpu] の少数パスによるインスタンス描画。盤面と演出を新規に描画し、HUD・ショップ・デバッグは [`egui-winit` / `egui-wgpu`][egui] で新規実装する。変更のないときは再描画を要求しない。日本語フォントは [Noto Sans CJK JP の OFL][noto] と起動時読込量を確認する。効果音は [`cpal`][cpal] に上限付きの発音イベントを渡して新規に合成し、音声コールバックで盤面ロックや動的確保をしない。 |
| 新規保存形式 | 型を固定した DTO と [`serde` + `postcard`][postcard] のバイナリを候補とする。版番号、長さ、世代、破損検出を付ける。整数は固定幅または正規化した長さ付き unsigned バイト列（順序を仕様化）とし、Rust の `usize` やライブラリー内部表現は保存に出さない。 |
| 永続化 | ユーザーデータ領域に単一書き手で保存する。I/O スレッドで同じディレクトリの一時ファイルに保存・同期し、OS 上で検証した置換処理を使う。直前の健全な世代を保持し、失敗・容量不足は通知する。 |

ネイティブは描画・入力のスレッドと盤面の単一所有スレッドを分離し、同時操作は後者が一列で確定する。機械ごとのスレッドや全体ポーリングは使わない。確定世代から変更チャンクの不変データ、短い HUD 更新、アニメ・音のイベントをまとめて渡す。描画側は共有された階層を可視範囲・LOD で絞ってインスタンスを作る。転送待ちの描画世代は差分を失わない形で集約してよいが、購入や反転入力を落とさない。長い処理は操作順を保って分割し、確定前の盤面を購入や保存に公開しない。カメラと入力の視覚的フィードバックは進められるようにする。

旧セーブは [原版 v2 の保存・復元](../../vendor/main.js#L646-L745) と [v1 変換](../../vendor/main.js#L747-L769) の参照・計測用入力に限る。初期版に読み込み・自動移行は入れない。移行が必要になれば別課題とし、旧データを書き換えない明示インポートと、論理状態・精度の検証を別途設計する。

主要 Rust 依存は MIT／Apache-2.0 系。依存バージョンは実装開始時に Rust stable との互換性、`wgpu` と `egui-wgpu` の組合せを確認して固定する。新規に採用する依存・同梱物のライセンスと通知は配布前に確認する。

### ビルド・配布

- **初期 CI は headless のみ。** [GitHub Actions の `ubuntu-24.04`][github-runners] で、PR ごとに format・Clippy・headless テスト・`x86_64-unknown-linux-gnu` の release ビルドを行う。この段階では UI／GPU／音声／保存をビルド依存に含めない。Rust ツールチェーンと `Cargo.lock` を固定し、ビルド・テストで `--locked` を使う。
- **製品の配布は Linux runner の GoReleaser を使う。** [組み込み Rust builder][goreleaser-rust] のある OSS v2.20.3 を固定し、`builder: rust`、`tool: cargo`、`command: build`、`targets: [x86_64-unknown-linux-gnu]`、`flags: [--release, --locked]` で通常の Cargo ビルドを行う。[既定の zigbuild と成果物パス][goreleaser-rust-source]に注意し、標準の `target` ディレクトリーと `release` プロファイルを使い、`binary` は実行ファイル名 `eight-times-eight` と一致させる。将来 Cargo workspace にする場合のみ、必要に応じて `--package=<名前>` を flags に足す。v2.20.3 の `healthcheck` は Zig を要求し得るが、通常の Cargo ビルドを使う `release` には不要なので初期 CI のゲートにしない。Pro の prebuilt builder は使わない。製品ビルドが整ってから [`goreleaser release --snapshot --clean`][goreleaser-snapshot] で未公開の配布候補を作る。[正式 SemVer タグの公開ジョブ][goreleaser-actions]は履歴を全取得し、そのジョブのみに `contents: write` と `GITHUB_TOKEN` を渡す。配布は `tar.gz` と SHA256 チェックサム、`vendor/` は同梱しない。設計確定の段階ではタグ発行・公開を行わない。
- **正式公開前に ABI と実機を検証する。** CI 成功だけで GPU 対応としない。最低対応環境を決め、古い ABI が必要なら対応下限のコンテナー／sysroot で依存も含めてビルドする。`readelf -V` で GLIBC／GLIBCXX の要求を調べ、ウィンドウ、音声、Vulkan ローダー／ドライバーの依存も確認する。`cpal` 採用時の Linux ビルドには ALSA 開発パッケージを入れる。最低想定環境で配布候補を展開・起動し、Linux 実機で Vulkan の描画・提示・性能を確認してから正式配布する。
- **Windows は後続候補。** Linux 上で MinGW-w64 の版を固定し、[`x86_64-pc-windows-gnu`][rust-win-gnu] を `cargo build --locked --release` でクロスビルドする。`cargo check` はリンク検証の代用にしない。MSVC は対象外で、[`wgpu` v30 の静的 DXC][wgpu-dxc]は使わない。Vulkan を初回候補とし、DX12 は FXC／動的 DXC を別に検証する。依存 DLL を調べ、実 Windows 上で配布候補の展開・起動・描画・入力と性能を確認するまで配布しない。

### Web を作る場合の条件（初期対象外）

- **GPU から直接表示する。** 新規のメインスレッド UI は [`transferControlToOffscreen`][offscreen-transfer] で得た描画面を transfer list に載せ、Dedicated Worker に一度だけ渡す。Worker が [`wasm32-unknown-unknown`][rust-wasm] + [`wasm-bindgen`][wasm-bindgen] のゲームコアと GPU レンダラーを所有し、`wgpu` の[ブラウザー WebGPU バックエンド][wgpu-browser]から [`OffscreenCanvas` の GPU サーフェース][wgpu-offscreen]へ直接描画・提示する。元の HTML Canvas は移譲前に `getContext` しない。
- **Wasm↔JS の全ピクセルは 0 B。** フレームだけでなくフォントアトラス・テクスチャのピクセルも例外にしない。フレームの CPU 側 RGBA、GPU 読み戻し、`ImageData`／`getImageData`／`putImageData`、フレーム `ImageBitmap` の移譲は使わない。素材は GPU 上で手続き的に生成するか、ブラウザー側でデコードと GPU アップロードを完結させ、境界をまたがせない。入力・HUD・座標／インスタンスなどの非ピクセルデータだけをまとめて渡す。ブラウザー内部のコピーや非ピクセル GPU アップロードまでゼロという意味ではない。条件を満たせない素材や機能は延期する。
- **線形メモリーの共有は必須にしない。** スレッド間で移譲するなら独立した `ArrayBuffer` を使う。Wasm の [`memory.buffer`][wasm-js] 自体は移譲できない。非ピクセル領域を JS の `TypedArray` で参照する場合、`memory.grow` 後に現在のバッファーからビューを再取得する。`SharedArrayBuffer`（SAB）は非ピクセルデータで共有の効果を実測できた場合だけ採用する。COOP／COEP を設定し、メインと Worker の [`crossOriginIsolated`][cross-origin-isolated] が `true` で共有経路が動作することを確認する。
- **成立しなければ出さない。** 対象の実機で secure context、Worker WebGPU／OffscreenCanvas の有無だけでなく、互換アダプター、デバイス取得、サーフェース構成と実際の描画・提示まで確認する。Worker 経路が成立しなければ、移譲前に判定するか失敗後に Canvas を差し替え、メインスレッドの直接 [WebGPU][webgpu] を試す。必要なら同じ制約で WebGL2 を比較する。性能・対応条件を満たす経路がなければ、Canvas 2D や CPU 描画に戻さず Web 版を出さない。

## 検証と採用・切替条件

### 原版の予備計測（候補スタックは未計測）

#### ロード時の境界再構成

`cfec14a` の [`load()` と補助関数](../../vendor/main.js#L686-L744) を計時用ページに挙動を変えず抽出し、Linux x86-64（Ryzen 9 9950X）、ヘッドレス Chrome 157.0.8103.78 で実行した。別プロセス・別プロファイルで 2 回、各ケースで毎試行盤面を作り直し、16 回ウォームアップ後に 40 回計測した。`localStorage` の `8times8.v1` に原点の完成区画一つ・機械なしの合成 v2 を置く。`done` は 1D で `{"4":["0,0"]}`、1E で `{"5":["0,0"]}`、いずれもアイテム取得済み、`groups`／`coarse` は空、入力は各 238 B。

| ケース | `touch` 呼び出し（別試行で計数） | p50（第1回／第2回） | p95（第1回／第2回） |
| --- | ---: | ---: | ---: |
| 1D | 2,048 | 3.095／2.790 ms | 4.225／3.455 ms |
| 1E | 16,384 | 26.288／24.003 ms | 35.175／27.235 ms |

原版 `saveNow()` が `groups`／`coarse` を出力した 1E の往復入力でも `touch` は 16,384 回、p50 は 29.403／26.745 ms。計時はキャッシュ済み `localStorage` の読み取り・JSON 解析・盤面再構成を含む同期 `load()` 区間のみ。保存書き込み・描画・起動は含まない。同サイズの合成入力でも辺が伸びると反復が増えることを確認したが、1F／1H は実行しておらず、Rust や Electron の性能との比較には使わない。

#### 初期 1A の単発描画トレース

ソース・資産を変更せず、`cfec14a` の `vendor/index.html` を Chrome 157.0.8103.78 のヘッドレスで起動した。1280×820 / DPR 1、ライトテーマ・効果音オフ、新規プロファイル、進捗セーブ・機械なし。初期 1A のタイル 27（0 起点）を左クリック 1 回し、反転が 0→1 枚になることを確認した。

再現時は、初期描画後に Chrome の [CDP `Tracing`][chrome-tracing] で `devtools.timeline` を取り、[原版のテスト用 `tileCenterScreen`](../../vendor/main.js#L2342-L2354) でタイル中央を求めてクリックする。クリックに続く描画用 rAF の [コールバック `frame()`](../../vendor/main.js#L812-L845) を `FunctionCall` から抽出する。12 回の経過時間（`dur`）は中央値 **0.326 ms**（0.228–0.529 ms）、同区間のスレッド CPU 時間（`tdur`）は中央値 **0.325 ms**、同コールバックの開始間隔（`ts` の隣接差）は中央値 **16.67 ms**。これは表示 FPS や GPU 時間ではない。単発の初期盤面だけなので、高負荷、Electron 実機、プロセス全体の CPU・RSS は未計測であり、原版全体やリライト後の性能には外挿しない。

### 実装時の検証

**疎な境界・空間索引の headless 採用ゲート。** 描画や保存層に進む前に、1D／1F／1H と小規模盤面・密な盤面で同一の可視領域を使う。疎な系列は非ゼロノード数を揃えて深さの影響を切り分け、区画の整列境界、負座標、辺の一部分だけの照会、境界の部分消費後の再照会を含める。

小規模では `vendor/` を正しさの基準とし、意図的な差異を除いた論理状態・出力順を完全照合する。合成盤面では 1B `(3,0)` 完成時に東辺の 1A `(28,0)` は未開放。後の 1C `(1,1)` 完成で進入可能になっても古い接触分の開放は増えず、照会順を逆にしても一致することを試す。1H など原版展開が現実的でないケースは実行せず、独立した座標・報酬の式と局所を素朴に展開する参照実装で確かめる。

固定した Linux 実機の headless release で、物理レコードの事前展開／遅延展開、直接走査／索引を片方ずつ切り替える。準備と変更・完了・境界の部分消費・可視照会・競合最近傍を分け、結果 0 件も含めて訪問ノード・生成／解放レコードを数える。解放・回収のコストを含めた各操作の p95 とピーク RSS（常駐分と操作中の追加分）を事前予算と比較する。出力件数固定で辺長と視野外ノード総数を別々に増やし、境界処理・照会のコストがいずれにも比例しないこと、断片が多い盤面で予算内、小盤面で非退行を採用条件とする。

1. **基準を取る。** Linux x86-64 GNU の headless release ビルドで固定入力を繰り返し、次に Linux 実機で Vulkan 描画・保存込みの基準を取る。端末、OS、GPU／ドライバー、ビルド設定、盤面分布・金額のビット長、解像度・DPR・カメラと入力量を記録する。音・ショップはオン／オフを分け、コールド起動とウォーム実行は混ぜない。原版は参照値とし、同条件・同区間で測れたケース以外の速度比は出さない。
2. **盤面と保存の代表シナリオ。** 初期 1A の連打と 64 枚目、[アイテム直前と 1D 直後の原版の状態](../../vendor/main.js#L1767-L1799)を参考にした合成入力、1D／1F／1H の完成、通常枠の上限まで配置した競合機械の最寄り探索を測る。ネイティブでは近接／全体ズーム、ショップでの購入、ドラッグ、確定世代の保存・ロードを別に測る。原版の参照実行は現実的なケースに限定する。
3. **論理挙動と厳密性を先に判定する。** 時計・乱数・入力列を固定し、親座標の `-5/-4/3/4` と許容域の端、機械予約・同時刻・移動中の段階変更、群の混在、報酬・開放・アイテム・親連鎖の順を照合する。初期盤面でタイル 27 から予算 128 を使う回帰例では、1A `(0,0)` の次に北 `(0,-1)` が完成する。`2^53±1`、`u128::MAX` 前後、価格の段階 78/79 と 2,581/2,582（次回価格の上限マーカー）、実効作業量の指数 51/52/53、残高＝価格／1 不足、1 ビット広い利用可能額、支出超過の 0 化を独立した厳密整数参照値で確認する。他レベルの残高による購入は不可。新形式では順序を含む往復一致、極端な件数・桁、破損、容量超過時の世代不変、中断・複数起動時の書き手制御と前回成功世代の復元を試す。
4. **主要指標はプレイ中の待ち時間。** 可視フレームの CPU 準備・GPU・提示間隔、入力から初回反応／操作確定までの時間、完成・探索・ロード・保存の p50/p95/p99、アイドル CPU、ピーク RSS、確保件数、訪問ノード数、描画インスタンス数、スレッド間・GPU 転送量、配布サイズと起動時間を記録する。提案目標は 60 Hz 動作中のフレーム生成時間 p95 ≤ 16.7 ms・p99 ≤ 33.3 ms、入力から初回反応 p95 ≤ 50 ms（意図した演出の待ちは分離計測）。UI を塞がないだけで合格にせず、確定までの時間も比較する。予算・対応機は基準計測後に決める。
5. **多倍長の切替はプロファイルを見て判断する。** [Criterion][criterion] で `u128` 昇格方式、`BigUint` 単体、`UBig` 単体を、少額・各昇格境界・256〜4,096 ビットに分け、加減算・比較・×3・有界累乗・十進変換・エンコードと確保件数を比べる。通常負荷の桁分布と巨大値だけの試験は別集計する。多倍長処理の寄与が大きく、純 Rust の代替が対象のエンドツーエンド p95 を繰り返し 10% 以上改善し、他の代表シナリオで有意な退行・精度差がない場合に切り替える。

Web を検討する場合は、コード経路の監査と境界のバイト数計測で、Wasm↔JS と Worker↔UI のピクセル転送が素材準備からフレーム提示まで **0 B**、読み戻しもないことを確認する。非ピクセル転送量、UI 更新・入力反応・描画／提示の p95、起動時間・Wasm メモリーを対象の実機で別に測る。`u128` に対応する [Wasm のネイティブ整数型][wasm-number-types]はないため、ブラウザー内で 33〜64／65〜128 ビットと各昇格境界を再計測し、ネイティブでの順位を流用しない。

設計の独立レビューと修正を 2 巡以上行い、承認済みの設計書だけをコミット・プッシュする。それまではコードを追加しない。その後、リポジトリのルートで最初の実装コマンドとして `cargo init --name eight-times-eight --bin --vcs none .` を実行する。`Cargo.toml` は手書きで作成せず、依存の追加には `cargo add` を使う。Git 設定は一切操作しない。

実装の順番は **再生用データと参照試験 → Linux で厳密整数コア・疎な境界と空間索引の headless 採用ゲート → ネイティブ UI・Vulkan 描画・新規保存 → Linux CI の release ビルドと実機検証 → release タグでの配布**。候補の切替は実測に基づく。Windows は実機検証後の候補、Web 版と旧セーブ移行は初期の順序に含めない。
